# Hardware Target Porting Guide

This guide describes how to add a new ESP32-family hardware target to QuotaFrame using the shared components and maintained-target registry.

## Third-party protocol devices

Third-party devices can implement the [open access contract](../protocol/open-device-access.md) without joining the registry or using Buddy. The minimum is secure passkey pairing, QF advertising, NUS JSONL, status and `usage.v1`; OTA, time and page controls are optional. Add devices explicitly through the Bridge.

## The maintained-target contract

Feature selection and UI belong to each target's maintainer. Devices may implement different features and interfaces according to their hardware, use cases, and maintenance capacity; support for one target does not require equivalent features on every other target. Advertise only capabilities actually implemented and validate the contracts of those capabilities.

Share UI behavior only where targets have the same maintenance boundary. The 480x480 AMOLED targets use [`usage_panel_state`](../firmware/components/usage_panel_state/README.md); rendering and calibrated orientation remain target-owned.

A maintained production target has two product-level integration points:

1. an ESP-IDF project under `firmware/targets/<target>/`;
2. one `TargetDefinition` entry in `bridge/src/quotaframe_bridge/targets.py`.

The registry defines maintained build targets, app image metadata, partition limits and release assets. Public BLE discovery and runtime labels do not depend on it: discovery uses QF advertising names plus NUS, labels come from validated status, and sessions come from `devices.json`.

CI, test builds and release assembly derive their target lists from this registry; consumers must not maintain separate device lists.

## Recommended bring-up order

A new board does not need to be registered as a maintained production target on the first commit. Bring it up locally first, then register it once its product contract is stable.

Recommended order:

1. create the target project under `firmware/targets/<target>/`;
2. make board initialization and display output work;
3. integrate input/navigation appropriate to the hardware;
4. reuse `usage_core` and `usage_protocol` for the dashboard data model and protocol;
5. integrate secure BLE through `usage_ble`;
6. integrate OTA through `usage_ota` when the target is intended to become maintained;
7. add target-specific logic tests for device logic that can run without physical hardware;
8. register the target once identifiers, advertising prefix, image names, release names, and required capabilities are settled;
9. complete hardware verification before claiming the target is supported.

Production targets should wire up `OtaSession::set_power_source()` at bring-up; boards without a readable PMIC may skip it for now, in which case no battery gate is applied.

## Directory layout

All production firmware projects follow the same shape:

```text
firmware/
├─ components/
│  ├─ usage_core/
│  ├─ usage_protocol/
│  ├─ usage_ble/
│  ├─ usage_ota/
│  ├─ usage_rtc/
│  └─ esp_desktop_buddy_folder_push/
└─ targets/
   ├─ m5sticks3/
   ├─ esp32_s3_touch_amoled_216/
   └─ <new-target>/
      ├─ CMakeLists.txt
      ├─ sdkconfig.defaults
      ├─ partitions.csv
      ├─ dependencies.lock          # generated by ESP-IDF Component Manager when applicable
      ├─ main/
      │  ├─ CMakeLists.txt
      │  └─ ... board-specific sources
      └─ test_apps/                 # optional target-specific buildable tests
```

Copy [`docs/porting/minimal-target/`](porting/minimal-target/README.md) into `firmware/targets/<target>/` and supply the board-specific configuration and logic. It is a structural example, not a complete BLE implementation or a registered target.

## Shared components

Use the shared components for behavior that is intentionally hardware-independent:

| Component | Responsibility |
| --- | --- |
| `usage_core` | usage model, last-known values, connection and data availability state, countdown formatting |
| `usage_panel_state` | page cycling, OTA touch routing, screensaver state, render scheduling, battery banding, persisted display settings |
| `usage_json` | strict raw JSON, UTF-8, duplicate-key and public name/version validation |
| `usage_protocol` | `usage.v1` parsing and validation |
| `usage_ble` | secure BLE session, bonding, event queues, protocol dispatch |
| `usage_ota` | OTA confirmation/session state, image validation/write flow, rollback integration |
| `usage_rtc` | PCF85063A local calendar read/write on a target-owned I2C bus |
| `esp_desktop_buddy_folder_push` | vendored Folder Push implementation used by the production OTA path |

The following should normally remain target-owned unless real duplication across multiple targets proves otherwise:

- panel/BSP initialization;
- LovyanGFX/LVGL setup;
- display transport and draw buffers;
- buttons, touch, gestures, and input routing;
- orientation and touch-coordinate mapping;
- brightness and power management;
- RTC, battery gauge, IMU, audio, SD, and other optional peripherals;
- layout and presentation decisions tied to screen geometry.

## Vendor power-management libraries

Power management stays target-owned, and vendor board-support libraries are the
usual source of surprises there. Treat their defaults and their register
decoding as claims to verify against the PMIC's own documentation.

**Check which rails the helper turns on for you.** Convenience initializers
enable peripheral rails whether or not the target uses them. `M5Unified`'s
`M5.config().output_power` defaults to true and enables the PMIC boost
converter; on a stick-class board that rail feeds a Grove/HAT header a display
panel never drives, and the converter then runs off the cell for as long as the
board is powered. Read the power-configuration register back after `begin()` and
compare it against the datasheet's documented reset value. A difference is a
rail something enabled on your behalf.

**Check whether the library decodes status registers correctly.** M5PM1's
power-source register is a bitmask — one bit each for 5VIN, 5VINOUT and
battery, and several may be set at once — while `Power_Class::getPowerSource()`
compares it against an enum and so reports `unknown` for every valid
combination. Read such registers directly when the decoded value drives
behavior.

**Check which controls genuinely exist.** M5PM1 implements charging as fixed
hardware behavior and exposes no charge-current or termination-voltage
register, so the corresponding `M5Unified` setters return failure. Charge
headroom on such a target is set entirely by input supply quality and the
board's own draw; no software knob compensates for either.

A battery percentage derived from a linear voltage map is a voltage proxy, not
a state of charge. Targets with a real fuel gauge report charge directly;
targets without one map a single voltage reading onto a straight line, which
tracks the flat middle of a lithium discharge curve poorly. A board that is
draining faster than it charges therefore reports a low but entirely truthful
percentage. Confirm the raw PMIC voltage before changing indicator logic.

## Target Registry fields

Maintained targets are declared with `TargetDefinition` in `bridge/src/quotaframe_bridge/targets.py`.

```python
TargetDefinition(
    id="example_target",
    label="Example-Board-1.23",
    firmware_project="firmware/targets/example_target",
    idf_version="6.1",
    ota_image="example_usage_panel.bin",
    full_image="example_usage_panel_full.bin",
    release_stem="example-target",
    image_chip_id=9,
    ota_partition_bytes=2 * 1024 * 1024,
    test_apps=("firmware/targets/example_target/test_apps/logic",),
)
```

Field contract:

| Field | Contract |
| --- | --- |
| `id` | Stable machine identifier. Must be unique. Do not rename after released firmware depends on it. |
| `label` | Official product name used by build and release tooling. Runtime Bridge labels come from validated `status.name`; devices with identical names receive address suffixes regardless of target. |
| `firmware_project` | Repository-relative ESP-IDF project path. Maintained production targets must live under `firmware/targets/`. |
| `idf_version` | Exact ESP-IDF version used by CI and Release. Its immutable container image must be registered in `IDF_IMAGES` in the same module. |
| `ota_image` | App image filename produced by the target build and consumed by release tooling. |
| `ota_partition_bytes` | Size of the smaller OTA app partition in bytes. Set `CONFIG_ESP_DESKTOP_BUDDY_FOLDER_PUSH_MAX_TRANSFER_BYTES` to this value plus 512 bytes for the manifest. Release assembly verifies both values. |
| `image_chip_id` | Espressif image-header chip ID used to validate release firmware: 9 for ESP32-S3, 32 for ESP32-S31. |
| `full_image` | Merged image filename used for first flash/recovery. |
| `release_stem` | Public filename stem using the brand and full official model name in lowercase, with decimal points omitted (for example, `waveshare-esp32-s3-epaper-397`). |
| `test_apps` | Optional repository-relative ESP-IDF test-app directories. Each declared app is built by the shared CI test-application job for its target's `idf_version`. |
| `web_flash` | Optional `WebFlashDefinition` (`name`, `description`, `chip_family`, `asset`). When set, the target appears in the browser flasher with its `-full-` image; the device photo `asset` is relative to `web/`. Omit it to keep the target out of the flasher. |

Device capabilities are declared by `status.caps`. Configure a `QF-` advertising prefix in the firmware; Bridge discovery does not read target-specific prefixes from this registry.

Shared component test apps under `firmware/test_apps/` are built once for every
distinct ESP-IDF version used by maintained targets. The test matrix is derived from the target registry without a separate workflow-owned version list.

Every test application for one ESP-IDF version is built by a single CI job,
which builds them in sequence. Production target builds keep one job each, so a
target failure is isolated and its dependency lock is verified on its own.

### Target identity

Keep the target `id`, BLE advertising prefix, OTA target identity and release
asset stem consistent across the registry, firmware and release configuration.
The OTA image must match the device hardware, partition layout and boot
requirements. Display names are separate from these machine-readable identifiers.

## ESP-IDF project setup

A target root `CMakeLists.txt` should explicitly expose only the shared components it needs. The maintained targets currently use repository-relative `EXTRA_COMPONENT_DIRS` entries such as:

```cmake
set(EXTRA_COMPONENT_DIRS
    "${CMAKE_CURRENT_LIST_DIR}/../../components/usage_json"
    "${CMAKE_CURRENT_LIST_DIR}/../../components/usage_core"
    "${CMAKE_CURRENT_LIST_DIR}/../../components/usage_protocol"
    "${CMAKE_CURRENT_LIST_DIR}/../../components/usage_ble"
    "${CMAKE_CURRENT_LIST_DIR}/../../components/usage_ota"
    "${CMAKE_CURRENT_LIST_DIR}/../../components/esp_desktop_buddy_folder_push")
```

Use the target's own `main/idf_component.yml` for board/BSP/component-manager dependencies. Commit the generated `dependencies.lock` for maintained production targets and verify that CI does not rewrite it after a clean build.

## Partition and OTA requirements

All maintained targets use dual OTA slots and ESP-IDF rollback. A new maintained target that enables the existing production OTA path should provide enough flash for:

- NVS and PHY data;
- `otadata`;
- two application partitions large enough for the built image;
- rollback-enabled bootloader configuration.

Do not copy partition sizes blindly from M5StickS3 or Waveshare. Size them for the target's flash capacity and actual firmware image.

Current production OTA also expects target identity, SHA-256 validation, physical confirmation, inactive-slot writing, reboot, and rollback confirmation. See `protocol/README.md`, `firmware/README.md`, and `docs/verification.md` before claiming OTA support.

## Target-specific tests

Test pure board-specific logic such as page transitions, orientation, scheduling, RTC conversion and OTA presentation in target test apps. Register their paths in `TargetDefinition.test_apps` for CI. Verify peripherals on hardware; avoid artificial hardware abstractions solely for unit tests.

## Build-only versus hardware-verified

Compilation does not verify physical display, input, pairing, memory peaks, peripherals or OTA behavior.

Use these evidence labels consistently:

| Evidence | Meaning |
| --- | --- |
| Build-only | Production firmware and declared test apps compile in CI. |
| Hardware bring-up | Board boots and core peripherals/display/input were observed on real hardware. |
| Hardware-verified | Required user flows were exercised on the actual board and recorded in `docs/verification.md`. |
| Maintained target | Registry entry exists, release/CI integration is active, documentation is current, and required hardware verification has been completed. |

## Maintained-target acceptance checklist

Before adding a new device to the maintained registry, confirm:

- [ ] ESP-IDF project is under `firmware/targets/<target>/`.
- [ ] Board initialization, display, and input work on physical hardware.
- [ ] `usage.v1` rendering works with real Bridge data.
- [ ] Secure BLE pairing/bonding and reconnect work on the target.
- [ ] Target ID is unique among maintained targets; the firmware advertising name follows the public `QF-<nonempty name>` contract. Advertising names may collide.
- [ ] OTA/full image filenames and release stem are final enough to publish.
- [ ] Partition table fits the target and matches the intended OTA policy.
- [ ] Maintained production targets implement `ota.folder.v1` and have recorded OTA hardware verification.
- [ ] Target-specific pure logic has buildable tests where worthwhile.
- [ ] Any test app paths are listed in `TargetDefinition.test_apps`.
- [ ] `idf_version` is exact and has a digest-pinned entry in Registry `IDF_IMAGES`.
- [ ] Clean CI builds do not modify committed dependency locks.
- [ ] Hardware evidence is recorded in `docs/verification.md`.
- [ ] User-facing README/firmware documentation identifies the new board accurately.
